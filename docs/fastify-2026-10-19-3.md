## Findings

### F-01 — Skip fallback-cache scans until an entry can expire (major at high cardinality, moderate)
- **File:** flarchitect/core/simple_cache.py:34-85
- **Category:** backend-efficiency
- **Problem:** Every `get()` calls `_purge()`, whose list comprehension walks every stored item even when no entry has expired.
- **Why it matters:** Cached reads scale linearly with total cache size instead of being constant-time between expiration boundaries. Real deployment usage is unknown; the benchmark establishes the cost only for this optional backend.
- **Fix direction:** Track a conservative earliest-expiry bound initialized to infinity. Lower it when setting an entry, reset on clear, and recompute while performing actual expiration scans. `_purge` must call the clock and skip scanning only if `now <= bound`. Otherwise retain global expired-key removal and compute the earliest surviving expiry in the same traversal; do not delay cleanup or change timeout interpretation. Protect get/set/clear/purge with one per-instance reentrant lock so a concurrent set cannot have its lowered bound overwritten by a stale purge result. Keep view execution outside the lock. Maintain the existing `_expires`, `_purge`, `cached`, get/set/clear public signatures.
- **Behavior risk:** Entries remain valid at exact expiry; zero timeout is not infinite; negative timeout expires on the next read; all expired entries must still disappear on any get, including misses. Test clock rollback, both overwrite directions, clear/reuse, successive expiration boundaries, cached falsy values and query-string distinction. Add deterministic concurrency coverage for the lost-bound-update race and an endpoint integration test forcing the fallback backend even though flask-caching is installed. Retain existing tests and compare complete seeded traces. Private dictionary mutation is not a supported API.
