# Fastify report — flarchitect, 2026-10-19

## Summary
Reviewed the model-to-route architecture, database operations, schema generation, configuration lookup, response decorators, authentication and optional caching. Architect discovers models and registers CRUD routes; database operations construct queries; AutoSchema generates serialization fields; response wrappers apply configuration and format the result. The three changes below remove redundant Python work without changing queries, public interfaces or response formats.

## Findings

### F-01 — Read detached-object policy only on detached errors (minor, trivial)
- **File:** flarchitect/schemas/bases.py:461-478
- **Category:** backend-efficiency
- **Problem:** `get_config_or_model_meta("API_SERIALIZATION_IGNORE_DETACHED", default=True)` runs on every field access, although only the exception handler needs it.
- **Why it matters:** Repeated per-field request-context and configuration work scales with rows times fields; 8,000 lookups in the baseline dump.
- **Fix direction:** Move the policy lookup into the DetachedInstanceError handler; otherwise retain the existing implementation.
- **Behavior risk:** Enabled policy must still return None for detached attributes, disabled policy must re-raise; normal and missing attributes must keep their outputs. Add focused tests for both policies and normal access.

### F-02 — Skip fingerprints when schema caching is disabled (minor, trivial)
- **File:** flarchitect/schemas/bases.py:609-632
- **Category:** backend-efficiency
- **Problem:** `cache_key = self._build_field_cache_key()` runs even when `use_field_cache` is false.
- **Why it matters:** All requests with query arguments and dynamic serialization build an unused fingerprint with nine configuration reads per schema.
- **Fix direction:** Build the key inside the first `if use_field_cache` branch. Leave generation and the second guarded cache write unchanged.
- **Behavior risk:** Cache-enabled paths still need their key; dynamic serialization and query arguments must retain their existing fields and outputs. Test both cache-enabled and bypass paths.

### F-03 — Return configuration cache hits before preparing lookup lists (minor, trivial)
- **File:** flarchitect/utils/config_helpers.py:113-149
- **Category:** backend-efficiency
- **Problem:** `method_based_keys`, `sources`, `keys_for_sources` and `keys_for_config` are constructed before the request-local cache is consulted.
- **Why it matters:** Configuration resolution is used throughout request processing, including serialization, and repeats list construction even for warm cache hits.
- **Fix direction:** Move those four preparations below the cache-hit return; keep normalized key and cache-key construction above it. Preserve the exact lookup expressions and source precedence.
- **Behavior risk:** Defaults remain uncached; positive values, method overrides, joined values and source reporting must be unchanged. Verify repeated hits, misses and isolation across requests with existing and focused tests.

## Not fixing
- API-key authentication scans users: a durable indexed lookup requires a key identifier/design decision and is outside this behavior-preserving pass.
- Optional fallback cache scans entries on every read: defer cleanup changes until workload/use is established.
- Duplicate relationship eager-loading construction and pagination filtering: ORM loader and count semantics need a separate focused investigation.
- Per-request signature introspection could be hoisted, but would stop reflecting runtime signature changes; defer rather than silently alter supported callable behavior.
- Response envelope case lookup can be hoisted, but the configuration cache improvement addresses repeated lookup costs across the library first.
